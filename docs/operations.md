# Operations

Runbooks for the things that change while the system is running. Everything here has a test
that exercises it; the test is named after each section.

## Rotating the JWT signing key

Access tokens are ES256 JWTs that live 15 minutes and name their key in the `kid` header.
Refresh tokens are opaque database rows, so a key rotation never signs anyone out.

1. `scripts/rotate-jwt-key.sh secrets/jwt.pem secrets/jwt-retired.pem`
   appends the current public key to the retired file and writes a fresh key in its place
   (the old file is kept as `jwt.pem.old`).
2. Deploy with `JWT_PREVIOUS_PUBLIC_KEYS_FILE=/keys/jwt-retired.pem` (or the PEM text in
   `JWT_PREVIOUS_PUBLIC_KEYS`, e.g. from a secrets manager). Every replica now signs with
   the new key and still accepts the old one; `/.well-known/jwks.json` lists both, the
   signing key first.
3. Once every replica runs the new key, wait one access-token lifetime, then empty the
   retired file and deploy again. Tokens signed with the old key now fail with 401 and the
   web client silently refreshes.

A leaked key is the same procedure with step 3 done straight away: the old key's tokens stop
working at once, and the clients refresh.

Test: `JwtKeysTest.tokensSignedBeforeARotationVerifyUntilTheOldKeyIsDropped`.

## Rotating the payment webhook secret

`MOCKPAY_WEBHOOK_SECRET` may list several secrets, newest first: `whsec_new,whsec_old`.

1. Deploy the API with `whsec_new,whsec_old`; it accepts webhooks signed with either.
2. Switch the payment provider to sign with `whsec_new`. Providers that sign with both
   during their own rotation window send two `v1=` values in one header; either matching is
   enough.
3. Deploy the API with `whsec_new` alone.

Test: `WebhookVerifierTest.acceptsTheNewAndTheOldSecretWhileTheSettingListsBoth`.

## Password-reset mail

The API sends mail over SMTP (`SPRING_MAIL_HOST`, `SPRING_MAIL_PORT`, plus
`SPRING_MAIL_USERNAME`/`SPRING_MAIL_PASSWORD` for a real relay such as SES SMTP).
Locally, compose runs Mailpit: open <http://localhost:8025> to read what was sent. Without a
mail host the API logs a masked address and never the link.

Test: `PasswordIT`.

## Switching payments to Stripe test mode

MockPay is the default, so the stack runs with no accounts. To use a Stripe **test-mode**
account instead (the adapter refuses `sk_live_` keys):

```sh
PAYMENT_PROVIDER=stripe
STRIPE_SECRET_KEY=sk_test_...
STRIPE_WEBHOOK_SECRET=whsec_...      # printed by `stripe listen`
stripe listen --forward-to localhost:8000/api/payments/stripe/webhook
```

Each order gets one hosted Checkout Session (idempotency key `order-<id>`). Stripe events are
translated into the same internal events MockPay sends (`checkout.session.completed` with
`payment_status=paid` → paid; `async_payment_failed`/`expired` → declined; a succeeded refund
→ refunded), so order transitions, de-duplication and the ledger are shared code.

What is verified, and how: `StripeClientIT` runs the adapter against
[stripe-mock](https://github.com/stripe/stripe-mock), which rejects any request that does not
match Stripe's OpenAPI spec; `StripeEventsTest` covers the event mapping; `StripeWebhookIT`
sends signed Stripe events through the real endpoint. stripe-mock returns canned responses,
so the full flow against a real Stripe test account has not been run in this repo.

## Monitoring

```sh
docker compose --profile observability up -d
```

Prometheus (<http://localhost:9090>) finds every API replica through Docker DNS and scrapes
`/actuator/prometheus` every 10 s (that path is not proxied by the web server, so it is
not public). Grafana (<http://localhost:3000>, opens on the dashboard, read-only without
signing in) shows traffic, p50/p95/p99 of placing an order, payment webhooks, dispatch
offers, outbox lag, live streams per replica, reconnects, cache hit ratio, search fallback,
DB pool and heap. Latency panels leave out the SSE `/events` routes, which stay open by design.
The dashboard is generated by `observability/build-dashboard.py`; edit that, not the JSON.

Alert rules (`observability/alerts.yml`, visible under Prometheus → Alerts): a replica down,
more than 1% 5xx, p95 of `POST /api/orders` above 500 ms for 10 min, outbox lag above 30 s,
repeated webhook signature failures, and search stuck on its Postgres fallback. No
Alertmanager is wired up, because there is nobody to page for a local stack.

Not included: distributed tracing. Each request is already one service plus its data stores,
and the slow paths are visible in the per-route histograms; an OpenTelemetry exporter is the
next step if a second service appears.

## When a dependency fails

Measured by `FaultIT`, which freezes each container with `docker pause` (the port still accepts
connections but nothing answers, so every client has to rely on its timeouts; this is harsher
than a stopped container). Numbers from one local run.

| Frozen | What customers see | How |
|---|---|---|
| Elasticsearch | Search keeps answering from Postgres (`degraded: true`, no pinyin or facets). First search 1.5 s, then ~15 ms. Back on Elasticsearch once it answers. | 1.5 s budget per query on a virtual thread; a timeout or I/O error opens a 10 s breaker, which closes early if the abandoned query completes. An error *returned* by Elasticsearch (e.g. index being rebuilt) only affects that request. |
| Redis | Menus, ordering, payment and sign-in keep working. The first menu request waits 2.1 s, later ones ~15 ms. No rate limits (fail open), no hot-dish list, no menu cache. | `RedisBreaker`: after one failure, optional Redis calls are skipped for 5 s. |
| Redis (events) | Live status, rider offers and hot-dish counts are held, then delivered 1–5 s after Redis returns. Search indexing carries on meanwhile (a dish change was indexed in 1.8 s while 20 live events waited). | Outbox: a failing topic is not retried within the same batch, Redis-bound topics are held while the breaker is open, and held events do not grow their backoff. |
| Postgres | Requests fail with `503` and `Retry-After` in 6–10 s instead of hanging. Readiness turns `503` (the replica leaves the load balancer); liveness stays `200` (no restart loop). Recovers by itself. | Hikari validation timeout 2 s, connect timeout 3 s, socket timeout 10 s; readiness includes the `db` check. |
| MockPay | Orders are created; the payment page link is retried on the next visit; refunds retry with backoff. | `OrderFlowIT` (provider-down cases). |

Shutdown: the API closes every live stream as soon as it starts shutting down, so browsers
reconnect to another replica and resume from their Last-Event-ID. Stopping a replica that held
10 of 20 open streams took 0.7 s (before: Tomcat waited for the streams until Docker killed it
at 10 s).
